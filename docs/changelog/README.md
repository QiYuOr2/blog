# 变更记录

> 每次改动代码行为，就追加一条记录。本页是索引与规范。
>
> 更新日期：2026-09-28

## 0. 为什么要记

变更记录只承担三件事：

1. 用一段话讲清这次改了什么、影响哪个页面/组件；
2. 把当时的量化结论（视口、尺寸、阈值）留下来，避免重复测量；
3. 写清验证方式与回滚方式，让改动可复查、可撤回。

## 1. 什么时候写

| 情况 | 是否写 |
| --- | --- |
| 改了页面的可见行为（布局、样式、文案、交互） | 写 |
| 修了 bug（含只在特定宽度/机型出现的问题） | 写 |
| 改了数据口径、构建/脚本行为 | 写 |
| 纯重构且行为等价 | 写一条“无行为变化”的简记录 |
| 改错别字、加注释、格式化 | 不写 |

## 2. 文件命名与结构

- 路径：`docs/changelog/YYYY-MM-DD-<kebab-slug>.md`，例如 `2026-09-28-heatmap-month-label-overlap.md`。
- slug 用**问题或改动本身**命名，不要用“update”“fix-bug”这类无信息量的词。
- 一条记录只讲一件事。同一件事的后续修正另起一条，并在两条正文里互相链接。
- 新增记录后，回到本页第 3 节索引表补一行（倒序，最新的在最上面）。
- 结构固定为 0–7 节，模板见 [TEMPLATE.md](./TEMPLATE.md)：

  0. 摘要（一句话 + 元信息）
  1. 现象
  2. 根因
  3. 方案取舍
  4. 实施步骤
  5. 验证
  6. 影响面与回滚
  7. 遗留 / 后续

## 4. 写法要点（渐进式披露）

- **摘要先行**：第 0 节读完要能判断“这条和我有关吗”。
- **数字留档**：涉及布局/性能的改动，记录当时测到的具体数值（视口、像素、阈值），而不是“有点窄”。
- **折叠细节**：推导过程、逐宽度测量表、方案对比放 `<details>` 里，正文只留结论。
- **可复跑**：验证一节写清命令或方法（如“无头 Chrome 复刻组件结构，视口 320/393/402px”），不写“已手动确认”。
- **可回滚**：写明改动范围（单文件/多文件）与回滚方式，能直接 revert 一个 commit 最好。
